01 — The problem

A single financial intention costs a dozen steps.

Paying a bill or sending money is one thought for the user and a chain of disconnected systems for everyone else.

01

Fragmented rails

Bills, wallets, bank transfers and merchant accounts each live in a separate app with its own flow and identifiers.

02

Language mismatch

Interfaces expect formal Arabic or English menus. People speak Iraqi dialect, half-sentences, and voice notes.

03

Manual context

The user re-supplies the same recipient, account and amount details to every channel, every time.

04

Late risk checks

Fraud and KYC problems surface after the transfer, in a support ticket — not before the decision.

02 — Our solution

One platform. Many agents. One accountable decision path.

This is not six disconnected AI features. It is one autonomous financial operating system whose agents collaborate to complete financial goals safely. One user goal → one orchestrator → multiple specialist agents → verified action.

Central orchestrator

A supervisor agent turns a stated goal into a plan and owns the outcome end to end.

Specialist agents

Narrow, testable agents for payment, fraud, KYC, verification, lending, merchants and support.

Shared memory & tools

One context store and one governed tool layer, so every agent sees the same facts and calls the same rails.

Permission boundaries

Autonomy is explicit: what an agent may do alone, what needs confirmation, what is blocked.

دزّيت فلوس بس ما وصلت.

What the agent owns

Understanding the goal, resolving recipient and biller, completing missing fields, preparing the transaction, executing against the payment tool, and confirming the result.

What it must never do

Move money on an unresolved recipient, skip the confirmation gate above the risk threshold, or report success it has not verified.

What "done" means

The executed transaction matches the user's stated goal on every field, the user was shown what they approved, and the result was read back from the rail.

JEV mode · fast decision & routing layer

A lightweight pass that decides how much machinery a request actually needs, so trivial requests never pay for a full reasoning pipeline. It answers, cheaply:

What does the user want? Which agent is needed? One agent or several? Is retrieval or data needed? Is an external tool required? Is the action sensitive? Is user confirmation required? Block or escalate?
Supervisor / orchestrator agent

Builds the plan, selects agents dynamically, sequences their calls, resolves conflicting outputs, holds the confirmation gate, and owns recovery when a step fails.

05 — Example end-to-end workflow

A high-value transfer, in full.

User

حوّل مليون دينار لهذا الحساب.

“Transfer one million dinars to this account.”

JEV
Sensitive action · multi-agent · confirmation required

Intent is a transfer, the amount is above the risk threshold, and the recipient is not a known contact. Routes to the supervisor with a full-pipeline flag.

Supervisor
Plans the chain

Payment → Fraud → KYC → Verification → confirmation gate → execution.

Payment
Prepares the transaction

Resolves the account, checks balance and limits, assembles amount, currency, recipient and reference. Flags that the recipient is new.

Fraud
Scores the risk

New recipient, high value, first-time pattern. Elevated but not blocking — returns the reasons, not just a score.

KYC
Checks the threshold

Confirms the user's verification tier permits this amount. If not, it returns exactly which requirement is missing.

Verify
Re-reads the original request

Compares the prepared transaction field by field against what the user actually said. Any mismatch stops the chain here.

Gate
Explicit user confirmation

The user is shown the recipient, amount and fraud reasoning in Iraqi Arabic and must approve. No approval, no execution.

Tool
Executes against the payment rail

Idempotent call with a request key, so a retry can never produce a second transfer.

Result
Confirms or recovers

Reads the settled state back from the rail and reports it. On timeout it checks status before retrying; on failure it explains the cause and offers the next step.

The same chain contracts for low-risk requests: a 10,000 IQD transfer to a saved contact skips fraud escalation and the confirmation gate, and executes in one hop.

07 — Autonomous decision loop

Agentic, not conversational.

The system does not answer a question and stop. It runs a loop until the goal is complete, blocked, or escalated.

01ObserveGoal, context, history
02UnderstandIntent + entities
03PlanSteps and order
04Select agentsOne or several
05ActTools and APIs
06VerifyMatch to request
07RecoverRetry, ask, escalate

The AI acts on its own to…

understand goals · create plans · choose agents · retrieve information · call tools · validate data · detect its own failures · retry safe, idempotent operations · route and escalate cases · verify results.

It stops and asks when…

the action moves money above a threshold · the recipient is new or ambiguous · the operation is irreversible · fraud or KYC signals are elevated · agents disagree · the user's intent has more than one plausible reading.

هذا الرقم ديتصل بيّ ويگلي انطيه رمز الـOTP.

→ fraud agent · block + educate

Recognized as an OTP-sharing scam. The system never assists the request, warns the user, and escalates.

Decision trace

Every request stores which agents ran, what each returned, why the route was chosen, and what the user approved — reviewable after the fact.

Idempotent execution

Payment calls carry a request key. Retries after a timeout reconcile against the rail instead of issuing a second transfer.

09 — Failure handling

Designed around the cases that actually occur.

FailureSystem response
Ambiguous requestAsks one targeted clarifying question instead of guessing — never resolves ambiguity by assumption on a payment.
Wrong or unresolved recipientPresents candidate matches with distinguishing detail; requires selection before preparing the transaction.
Missing payment informationNames the specific missing field and requests only that, preserving everything already gathered.
Suspected scamBlocks, explains the pattern in the user's dialect, and escalates rather than completing the action.
Insufficient KYCStops before execution, states the exact unmet requirement, and hands off to the KYC flow.
Payment API unavailableReports honestly, offers to retry, and never reports a success it could not confirm.
Duplicate transactionDetected by request key and recent-transaction check; surfaced to the user instead of executed twice.
Conflicting agent decisionsSupervisor applies precedence — safety agents override convenience — and escalates when the conflict is unresolvable.
Tool timeoutStatus is reconciled before any retry; ambiguous outcomes escalate rather than repeat.
Unsupported requestDeclines clearly and routes to the correct channel instead of improvising a partial action.

Held-out test set

A set of Iraqi Arabic financial requests — including adversarial, ambiguous and scam cases — written separately and withheld during development. Reported numbers come from this set, not from examples the system was tuned on.

Synthetic data, no real customers

All development and testing runs on generated data. No real customer financial data is required.

The remaining agents

We deeply build and evaluate the payment and transfer workflow first. The remaining agents share the same architecture and demonstrate the platform's expansion path.
Closing

Financial software in Iraq should understand how Iraqis actually speak, and act on what they actually mean — safely, and end to end. We are building the autonomous layer that does it: one goal, one orchestrator, many agents, one verified action.
