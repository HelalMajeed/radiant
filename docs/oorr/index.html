OORR AI API

OORR AI is an Arabic-first tutoring model served by Radiant. Its current production model is Sargon 1.5. This is the reference for its HTTP API: how to call chat and image requests, what the responses contain, how tokens are counted, and which limits apply.

Introduction Live

OORR AI answers students' questions in Arabic in the voice of an Iraqi teacher, working through problems step by step. Radiant is the platform that exposes it; Sargon 1.5 is the model that answers. The API below is the deployed, production surface.

What Sargon 1.5 does today

  • Arabic tutoring chat. Explanatory, step-by-step answers in Modern Standard Arabic, with familiar Iraqi phrasing where it helps.
  • Subject and grade scoping. Optional subject and grade fields steer the answer toward a student's stage and course.
  • Educational image understanding. Send a photo of a question, diagram or worked page and the model reads and explains its educational content.
  • Handwritten maths. Images marked kind: "handwritten_math" are transcribed before the tutor answers.
  • English curriculum books. A dedicated response policy applies to the two Grade 6 scientific English books (student book and activity book).
  • Short conversation memory. Prior turns of the same chat can be supplied with each request.

Retrieval-backed curriculum grounding is not live

OORR AI is trained and prompted as an Iraqi-curriculum tutor, but answers are not currently retrieved from or cited against textbook sources. The textbook retrieval subsystem exists behind the TEXTBOOK_RETRIEVAL_MODE flag, is off by default, and in shadow mode runs entirely off the response path for diagnostics — it never influences an answer.

The production system prompt explicitly instructs the model not to claim it has consulted the Iraqi curriculum or any specific study source. Treat answers as tutoring, not as sourced curriculum citations.

Set a generous timeout

Tutoring answers routinely take longer than a typical default. OORR's own clients use a 90 second request timeout. Use /api/tutor/stream if you want tokens as they are produced.

Authentication Pending

API-key authentication is not deployed yet

There is currently no API-key system on the OORR API. The tutor endpoints accept no Authorization header, and no key is issued, validated or revoked anywhere in the deployed service. Anything on this page describing bearer keys is a planned contract, not a live one.

How requests are identified today

The caller supplies its own userId in the request body. That value is what the server uses for rate limiting, daily token allowances and usage accounting — it is not authenticated, and it is not proof of identity.

MechanismWhereProtectsStatus
userId in body/api/tutor*Rate limit, daily allowance, usage rowsLive
Session cookie/api/auth/*Signed-in student accounts (WhatsApp OTP)Live
Authorization: Bearer/api/tutor*Developer API keysPending

The existing account auth is a passwordless WhatsApp one-time-code flow that issues an HttpOnly session cookie. It authenticates students in the OORR app; it is not a developer credential and does not grant API access.

Planned bearer-key contract Pending

When key auth ships, it is intended to look like the following. Do not build against this yet — the header is currently ignored.

Planned — not yet accepted
curl -X POST https://api.oorr.ai/api/tutor \
  -H "Authorization: Bearer $OORR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "message": "اشرح قانون أوم بإيجاز", "modelTier": "basic" }'

Under that design the key identifies the caller, so userId becomes optional and rate limits, allowances and usage attach to the key rather than to a self-declared id.

Models Live

Sargon 1.5

OORR AI's current production model for chat, Iraqi curriculum assistance and supported educational image understanding.

FieldValue

StatusLive

Every successful response reports "model": "sargon-1.5". This is a stable public identifier: you integrate against Sargon 1.5, and the infrastructure that executes a request is managed by Radiant and may change without notice or API impact.

Capability tiers

modelTier selects how much capability a request is served with. It is a service-level setting on Sargon 1.5, not a different model — the reported model is sargon-1.5 in every case.

TierBehaviourStatus
basic Default. Standard chat and image understanding. Live
pro Higher-capability reasoning, gated by a per-caller trial quota. Returns a proTrial object describing remaining quota. Live
ultra Accepted by the validator only so it can be refused explicitly. Always rejected with 503 ULTRA_UNAVAILABLE — never served and never silently downgraded. Pending

If modelTier is omitted the server derives it: basic, unless the legacy combination plan: "premium" with complexity: "complex" is sent, which resolves to pro. Sending an unrecognised tier is a 400 INVALID_REQUEST.

Capabilities by request shape

A text-only request is answered as chat. A request carrying image is answered with image understanding. image.kind: "handwritten_math" tells Sargon the image is handwritten mathematics so it is transcribed before being answered.

Execution is managed by Radiant

How a request is executed — and on what infrastructure — is not exposed and is not selectable. You send a request to Sargon 1.5 and receive an answer with its token counts; there is no field to read or set that changes this.

const reader = res.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
let answer = "";

while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });

  const frames = buffer.split("\n\n");
  buffer = frames.pop() ?? "";

  for (const frame of frames) {
    const event = frame.match(/^event: (.+)$/m)?.[1];
    const data = JSON.parse(frame.match(/^data: (.+)$/m)?.[1] ?? "{}");

    if (event === "delta") answer += data.text;
    if (event === "done") console.log(data.totalTokens, "tokens");
    if (event === "error") throw new Error(data.code);
  }
}

Size the payload, not just the file

The 10 MiB cap is on the decoded image. Base64 adds roughly one third, and the server rejects an oversized request on the encoded length before it allocates memory to decode — so an over-cap image fails fast with 400 INVALID_REQUEST.

Two quirks worth knowing

plan is required by the validator even though the server immediately normalises it to normal. Omitting it is a 400, so send "plan": "normal" and select capability with modelTier.

Unrecognised fields in the request body are ignored. There is no field that selects or influences how Sargon 1.5 executes your request.

Token usage

Token counts come back on every successful response and, for streaming, on the terminal done event. Each request is also metered server-side — inputTokens, outputTokens, totalTokens, latencyMs, success, and the request type (text, vision, math_ocr, premium_reasoning).

Usage rows never contain prompts, questions, answers, image data or credentials. Aggregation resets daily on the Asia/Baghdad calendar day.

These counts are recorded, not yet priced

Token accounting is real and persisted. Converting it into a monetary amount is not implemented in the service — no cost field is computed, stored or returned. See Pricing.

The cooldown is enforced atomically and persists across restarts. It is reserved once per accepted request, so an internal retry still counts as a single request. The server is the single source of truth for the pace — mirror Retry-After rather than hard-coding an interval, and note that a cooldown storage fault denies the request rather than letting it through.

Handling 429 correctly

async function askWithRetry(body: unknown, attempts = 3) {
  for (let attempt = 1; attempt <= attempts; attempt++) {
    const res = await fetch("https://api.oorr.ai/api/tutor", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(body),
    });

    if (res.ok) return res.json();

    const err = await res.json();

    // Never retry a validation or safety failure — it will fail identically.
    if (err.code === "INVALID_REQUEST" || err.code === "CONTENT_BLOCKED") {
      throw new Error(`${err.code}: ${err.error}`);
    }

    // Obey the server's pace; fall back to the header, then a sane default.
    const wait = err.retryAfterSeconds
      ?? Number(res.headers.get("Retry-After"))
      ?? 30;

    if (attempt === attempts) throw new Error(`${err.code} after ${attempts} attempts`);
    await new Promise((r) => setTimeout(r, wait * 1000));
  }
}
import time
import requests

NO_RETRY = {"INVALID_REQUEST", "CONTENT_BLOCKED"}

def ask_with_retry(body, attempts=3):
    for attempt in range(1, attempts + 1):
        res = requests.post(
            "https://api.oorr.ai/api/tutor", json=body, timeout=90
        )
        if res.ok:
            return res.json()

        err = res.json()
        if err.get("code") in NO_RETRY:
            raise RuntimeError(f"{err['code']}: {err['error']}")

        wait = err.get("retryAfterSeconds") or int(
            res.headers.get("Retry-After", 30)
        )
        if attempt == attempts:
            raise RuntimeError(f"{err.get('code')} after {attempts} attempts")
        time.sleep(wait)

Rates are published; metering-to-cost is not implemented

The service records token counts, but it does not compute, store or return a monetary amount, and there is no billing, invoicing or payment path in the deployed API. These rates are the stated commercial terms, not a value read back from the system.

Estimating a cost yourself

Because token counts are real, you can price a request client-side from the response. Both figures are billed per million tokens.

Client-side estimate
const INPUT_PER_1M = 1.80;
const OUTPUT_PER_1M = 3.60;

function estimateUsd(res) {
  const input = (res.inputTokens ?? 0) / 1e6 * INPUT_PER_1M;
  const output = (res.outputTokens ?? 0) / 1e6 * OUTPUT_PER_1M;
  return input + output;
}

// 412 input + 735 output tokens → about $0.00338

Token fields are optional: when a count is not reported for a request it is absent, so treat a missing count as unknown rather than as zero.

Intended key handling Pending

These are the rules the implementation is specified to follow:

  • Shown once. The full secret is returned only in the response that creates it, and is never retrievable again.
  • Stored hashed. Only a hash is persisted, matching how the existing service already stores session tokens and one-time codes.
  • Masked thereafter. Listings return a prefix and last four characters only — enough to tell keys apart, never enough to use one.
  • Renameable, revocable. A label can change freely; revocation is immediate and irreversible, and a revoked key is rejected before the request is served.
  • Attributable. Rate limits, daily allowances and usage rows key off the API key instead of a self-declared userId.

The "Copy" action is only meaningful at creation time, when the plaintext secret is briefly in hand. For an already-listed key there is nothing to copy but the mask — which is why it is disabled here rather than silently copying a useless string.
